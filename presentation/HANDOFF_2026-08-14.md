## Intended scientific story

The project is primarily a model-diffing study, not a benchmark-optimization or steering-only study.

The core claim under investigation is:

> Behavioral differences between a base and a fine-tuned model can be decomposed into task-level transitions, connected to shared sparse CrossCoder features, interpreted using semantics and timing, and tested causally with controlled steering.

The presentation uses DeepSeek base versus fine-tuned as the first case study. `DSTK100` is an internal communication name for the canonical same-text, layer-16, 16,384-latent, ReLU + exact TopK-100 CrossCoder trained for 10,000 steps. It is not the name of a published architecture.

## Confirmed behavioral results

DeepSeek base versus fine-tuned:

| Benchmark | Base pass | Fine-tuned pass | Pass-rate change |
|---|---:|---:|---:|
| HumanEval+ | 62/164 (37.80%) | 99/164 (60.37%) | +22.57 pp |
| BigCodeBench | 264/1,140 (23.16%) | 346/1,140 (30.35%) | +7.19 pp |

One-sided transitions used by the DSTK100 transition audit:

- 343 total;
- 257 improvements: base fail → fine-tuned pass;
- 86 regressions: base pass → fine-tuned fail;
- HumanEval+: 42 improvements and 7 regressions;
- BigCodeBench: 215 improvements and 79 regressions.

The qualitative direction agrees with ReCatcher: Kotlin fine-tuning improved aggregate General Logic while still introducing localized regressions. ReCatcher magnitudes are not directly comparable because it used 10 generations per prompt and its own regression-percentage definitions; this project used one canonical generation per task and official paired evaluation.

## Exact origin of feature 6404

### Initial statistical screen: regressions

Feature 6404 was initially nominated by the general BigCodeBench **regression** screen, not by an improvement-specific contamination screen.

For that screen:

- population: 268 tasks where the base model passed;
- positives: 79 base-pass → fine-tuned-fail regressions;
- controls: 189 both-pass tasks;
- aggregation selected for 6404: `max`;
- ROC-AUC: 0.6405;
- PR-AUC: 0.4049, prevalence 0.2948, lift 1.3735×;
- effect/permutation variability (E/V): 4.4651;
- positive support: 47/79;
- nominal permutation p: 1/201 ≈ 0.00498, not maxT-corrected in this initial screen.

The complete sensitivity audit showed that, for BigCodeBench regressions, ranking only by E/V, including all four aggregations, or applying/removing the auxiliary ROC/support filters recovered the same Top 10. Feature 6404 remained #2.

This screen nominated 6404 for investigation. It did **not** directly identify the later 80-case causal cohort.

### Later mechanistic hypothesis: improvements

The causal result was built from BigCodeBench **improvements**:

- base failed;
- fine-tuned passed;
- the base output contained generated test/import contamination;
- feature 6404 was naturally active in the base output.

The final cohort contains 80 tasks. Steering was applied to the base model to test whether suppressing 6404 could reproduce part of the fine-tuned improvement mode.

At `alpha=-2`:

- 19/80 became official passes;
- 41/80 lost test/import contamination;
- norm-matched orthogonal sham: 0/80 passes, 0/80 cleanup;
- matched CrossCoder features: at most 3/80 passes.

Therefore the supported causal statement is:

> In a selected base-fail/fine-tuned-pass contamination cohort, gated suppression of feature 6404 in the base model specifically altered the failure mode and recovered official passes.

It is not correct to say that suppressing 6404 repaired fine-tuning regressions.

## Critical narrative discontinuity to fix

The final deck currently presents:

1. slide 6/7: feature 6404 as #2 with `47/79` support from the regression screen;
2. later slides: `119/215` improvements, 80 improvement cases, and causal steering in the base model.

Without an explicit bridge, the audience may infer that the regression screen directly produced the causal improvement cohort. That is false.

Recommended bridge text:

> “The initial regression screen nominated feature 6404. Semantic follow-up across all transitions redirected the causal hypothesis toward a major improvement mode: post-solution test/import contamination in the base model.”

The scientifically honest discovery chain is:

```text
general regression screen nominates 6404
→ semantic inspection: expected / should / assumptions / comments / boilerplate
→ transition taxonomy reveals a compatible improvement mode
→ enrichment of 6404 in contamination improvements
→ 80-case mechanistic cohort
→ gated causal suppression in the base model
```

This is an iterative hypothesis-revision story, not a direct confirmatory pipeline.

## Taxonomy status: correction and validation need

The failure taxonomy **was run over all one-sided transitions**, not regressions only.

Evidence in `tools/analyze_transition_failures.py`:

- it iterates over every task with different base/fine-tuned labels;
- labels each case as `regression` or `improvement`;
- identifies the failing model accordingly;
- writes `transition_failure_cases.csv` and `failure_category_summary.csv` for both directions.

The reported `119/215` therefore comes from BigCodeBench improvement cases.

However, the taxonomy is rule-based and the report itself says audit candidates manually. Required validation before strengthening the claim:

1. Reproduce the 215 BigCodeBench improvement denominator from canonical labels.
2. Recompute the 119 contamination flags from the canonical repaired code and evaluator errors.
3. Manually audit a random sample of positive and negative classifications.
4. Report false-positive/false-negative estimates or inter-rater agreement if manual labels are created.
5. Confirm that “test/import contamination” is not conflated with missing required imports, syntax errors, ordinary examples, or harmless comments.
6. Version the exact taxonomy rules and cohort manifest used to select the 80 causal cases.

## Screening methodology clarified during presentation work

Four task-level activation summaries were calculated:

- `max`;
- `early_max` over the first 25% of evaluated tokens;
- `mean`;
- `active_fraction`.

For each feature and task:

```text
delta = aggregate(fine-tuned-generated text) - aggregate(base-generated text)
```

For a transition analysis:

```text
effect = mean(delta in positive transitions) - mean(delta in controls)
```

Labels were shuffled 200 times within benchmark and transition direction. Each shuffle recomputed the feature effect. The central ranking score was:

```text
E/V = observed effect / SD(permuted effects)
```

E/V is an empirical permutation signal-to-noise score. It is not a z-score, a p-value, or a probability of causality. The initial screen also computed a separate nominal permutation p-value; with 200 permutations its minimum was 1/201. The initial 6404 result was not maxT-corrected across 16,384 features.

In the BigCodeBench regression case, effect and E/V rankings were almost redundant (Spearman ≈0.999), and ROC/support did not change the Top 10. This should be described as one primary score plus diagnostic guardrails, not four independent pieces of statistical evidence.

## Feature selection principle developed during review

The presentation should emphasize the triad:

```text
MEANING ↔ FAILURE MODE ↔ TIMING
```

- Meaning: top activating tokens and contexts.
- Failure mode: which explicitly classified behavioral transition is enriched for the feature.
- Timing: whether activation occurs before or near the decision/error boundary.

Semantic clarity alone is insufficient. A late feature may be a consequence or a style marker. Statistical association alone may identify lexical/domain detectors. Timing alone does not provide semantic specificity.

## Token-level example caveat

The final slide uses BigCodeBench/668 as a compact example. It shows:

- baseline excerpt ending in generated tests/imports;
- steered output without the test-module import;
- online 6404 gate activity in the steered trajectory.

But the displayed function body also changes (`return []` versus `return min_subsequence`). This example does not isolate “same solution, cleaner stopping” perfectly. Before final publication, search the 19 corrected cases for an example where:

1. the function body before contamination is identical or nearly identical;
2. the first changed token is close to the test/import boundary;
3. the steered generation stops or avoids the import;
4. 6404 is active before that boundary;
5. extraction v4 and official evaluation clearly explain fail → pass.

If no such example exists, revise the claim: steering changes the autoregressive trajectory, sometimes affecting both implementation and stopping behavior.

## Non-monotonicity

The dense curve has two effective regions near `alpha=-0.5` and `alpha=-2`, with performance collapsing again at stronger suppression. The current hypotheses are:

- discrete token and top-p boundaries;
- one changed token changes the future context;
- future CrossCoder gates then change;
- pass/fail is discontinuous;
- large interventions leave the natural activation regime;
- one generation seed per task makes the pass@1 curve noisy.

This is a result worth preserving, but the exact curve shape should not be treated as stable until multi-seed replication.

The repository also contains a CodeLlama base-versus-merged case:
